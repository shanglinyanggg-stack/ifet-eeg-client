# iFET 四通道眨眼音量控制算法 v1.0.21

## 功能定义

- 连续自然眨眼 3 次：音量降低一个 App 配置步长。
- 连续自然眨眼 5 次：音量升高一个 App 配置步长；在确认窗内始终优先于 3 次。
- 算法输出动作 flag，App 执行音量变化。算法不直接操作系统音量。
- Python sidecar 是正式判定路径；TypeScript 本地算法仅是服务不可用时的保守降级路径。

## App 必须提供的输入与流程

1. 以 100 Hz、同一时间轴输入 EEG1-EEG4、IMU 和逐样本 valid 标志。缺失样本必须标为 invalid，不得用重复值冒充有效数据。
2. 每次佩戴先完成眨眼个体测量：3 秒睁眼安静、不眨眼；随后 10 秒连续自然眨眼，建议间隔 0.5-1 秒，保持头、下颌和电极不动。
3. 校准至少获得 5 个成对有效峰、一致率至少 65%、中位强度至少 3 robust-z，否则 App 必须提示重测并禁止音量动作。
4. 音量控制只在 `blink_control_ready=true`、`blink_baseline_stale=false` 且信号有效时执行。
5. App 必须展示启用/暂停配对、自动恢复进度和模板匹配状态，便于现场判断是动作失败还是信号失败。

## 判定链

原始 EEG 先经过严格因果的 2 阶 Butterworth 0.7-15 Hz 滤波。校准得到各通道中心、robust scale、眨眼模板、宽度、强度和节律。在线候选峰必须同时通过：

- 同一固定配对双通道同步响应；
- EEG1+EEG2 主配对支持；
- 运动、丢包边界、峰宽、难应期和振幅连续性门控；
- 与个体眨眼模板的相关性门控；
- 8 秒滑窗内的 3/5 次节律与结束等待窗。

正常质量下保留四通道信息。若 EEG3+EEG4 的噪声尺度超过校准参考 1.75 倍，并且超过 EEG1+EEG2 相对尺度 1.5 倍，则切换为 EEG1+EEG2 主导；EEG3+EEG4 只能在 EEG1+EEG2 同时支持时补充，不能独立触发命令。连续异常 burst 会先隔离对应配对，而不是让辅助配对噪声暂停全部控制。

无模板的保守群组峰高保持 2.5 robust-z。只有当该门已找到至少 3 个保守峰时，才用 1.8 robust-z 搜索是否存在较弱的第 4/5 峰；扩展成 5 次必须至少 80% 的峰得到个人模板支持。低阈值不会独立创建新手势，因此不会把安静段直接变成命令。

## 基线漂移与自动恢复

基线只在非眨眼、低运动、有效信号窗更新，闭眼 Alpha 状态不参与眨眼基线判断。连续 3 次健康检查超限会暂停受影响配对。暂停后仍运行独立恢复监测：使用最近 8 秒安静背景和最近模板确认的眨眼证据重估中心/尺度；普通漂移连续 3 次通过、burst 隔离连续 5 次通过后自动恢复并重新开启控制。恢复期间 App 不得执行眨眼音量 flag。

不要在眨眼 burst、头动、掉线插值段或电极重新佩戴瞬间更新基线；这些数据会把伪迹学成“正常”。电极位置发生实质变化时仍应让用户重新校准。

## 与睡眠音乐引导的关系

- Alpha 音乐开启使用个体睁眼 Alpha 基线、动态开启/关闭阈值和双通道一致性，不以闭眼基线实时下移来追随当前闭眼状态。
- 睁眼基线只能在确认清醒、睁眼且低伪迹时慢速更新；闭眼或疑似入睡时冻结，否则会抬高参考并造成闭眼后迟迟不开音乐。
- 睡眠分期和音乐控制使用独立状态机。分期的睡眠概率不能直接绕过音乐控制的确认时长、信号质量和冷启动门控。
- App 应显示 `alpha_ratio`、`alpha_on_threshold`、当前睁眼基线相对初始值的变化，以及算法服务/降级路径状态。

## 当前验证边界

开发标注集 136 组回放中正确 126 组（92.65%）：无动作 11/12、3 次 47/52、5 次 68/72。合成流验证了 3 次和 5 次动作、EEG3/4 成对伪迹拒绝、辅助配对隔离，以及主配对基线 3 秒恢复。详细结果见 `validation/adaptive_blink_v121_report.json`。

最新三次真机记录采用保存的最终个体模板做确定性复放：关闭模板补峰时正确 15/23；采用 1.8 robust-z 模板补峰后正确 19/23（无动作 2/2、3 次 6/7、5 次 11/14）。1.6 以下开始增加 3 次误延长为 5 次，因此未采用。详细结果见 `validation/latest_headset_replay_v121_report.json`。该复放从第一个样本即恢复了会话末保存的模板，不能替代重新佩戴后的前瞻真机验证。

这些结果来自单佩戴者开发数据，不是跨人群临床验证。正式 App 发布前应在不同佩戴者、不同松紧度和低质量场景进行前瞻测试，报告 0/3/5 混淆矩阵、每小时误触发数、恢复时间、丢包率和 Wilson 95% 置信区间。
